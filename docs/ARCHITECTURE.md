# Architecture inventory and implementation boundary

The initial `/Users/nkov/open-assist` repository contained only the 39-page strategy PDF and Git metadata. No existing desktop framework, capture layer, executor, provider integration or agent loop was present. The nearby `coasty-local-agent` was inspected read-only: it is a small Python/mss/PyAutoGUI example using a stateful Coasty API, not the multi-provider Open Cowork application described in the report. No existing application was rewritten or changed.

This repository implements a macOS-first desktop alpha: an Electron menu-bar application with separate pill and settings renderers, a TypeScript state machine, independent Swift speech and computer-control processes, encrypted append-only history, opt-in contribution tools and a synthetic Gym starter. The renderer has no Node or arbitrary IPC access. Provider requests originate in the main process. The model has no shell, file-reading, DOM or application API tools. Its only non-GUI capabilities are the launch-only `open_app` action and `open_file`, which opens a document or folder listed by the local system index with its default app; everything else is one validated mouse/keyboard action per observation. Bounded accessibility text and grounded controls are observation data, not a callable full-tree inspection tool.

`open_app` takes a plain name only (no paths, arguments, URLs or documents). The native helper resolves it against fixed allow-listed application folders (`/System/Applications`, its Utilities, `/Applications` and its subfolders, `~/Applications`, the system app cryptex, plus Finder): an exact name match first, then a unique whole-token match (“Chrome” → Google Chrome); several bundle identifiers are ambiguous and return up to five candidate names. Candidates must be foreground, non-background Mach-O application bundles. Installer/uninstaller/setup/updater/migration names, a built-in floor (Terminal, iTerm, Script Editor, Automator, Disk Utility, Keychain Access, Installer, Migration/Boot Camp Assistant, Spotlight, Siri, Open Assist itself), AppleScript/Automator applets and web-app wrappers, and the configured protected apps are refused. Policy allows only a resolved, unprotected result; unresolved/ambiguous names return `RETRY` with candidates, and refused names `DENY`. At execution the helper re-resolves the name, re-reads the bundle, checks it still matches the binding verified for that frame, and then activates or launches exactly that bundle without adding recent items.

Each capture adds `context.controls`: up to 60 visible controls of the focused window (role, name, enabled state and center as screenshot fractions). In browsers a breadth-first walk of the web area (at most 2,500 nodes and 250 ms) adds links, buttons, fields and toggles. Names come from title/description (and value only for non-editable controls); editable fields expose only their title, description or placeholder, and secure fields are skipped. The main process validates the list strictly (≤60 items, label ≤80 characters, coordinates within 0–1) and redacts detected credential spans. Grounding only suggests coordinates; every click is still hit-tested and evaluated by policy. The page host from a window document URL, or from the first `AXWebArea` URL (Safari), feeds protected-domain checks.

The native voice process owns Option-Space key-down/up. Key-down latches the controller via SIGUSR1 before JS handles the event and requests haptic feedback on supported hardware. A 160 ms hold starts microphone capture and on-device streaming recognition; a tap opens text input. Release stops audio and waits for a final recognition result, up to 1.8 seconds. Partial transcripts update the pill and may take one early step; stop and pause intents are routed from the final transcript. The early step (`src/voice/early.ts`, `electron/early-start.ts`) opens the app a request starts with ("open Slack and…") once the partials have settled on its name, before any run exists: it uses the Runner's own native sequence (surface, surface policy, capture, `surface(open_app)` with its launch binding, policy, execute), accepts only ALLOW, lifts the stop latch only inside resume → capture/execute → stop, and is gated off whenever a run is active, settling, waiting for approval, queued or starting. When the final transcript still begins with that clause and starts a run, the step becomes the run's prelude: `Runner.start` journals its frame and step as the run's first (`ActionExecuted` with `early: true`), the model's history starts with its result, a recalled plan that opens the same app continues at its next step, and a request that was only "open Slack." completes on the first capture. Otherwise nothing is recorded and the app stays open. Key-down pauses a working run, and speech with no usable command leaves it paused. An empty terminal result after release/the silence endpoint preserves the latest nonempty hypothesis as a recovered command, with zero approval confidence. A finalized correction stays in the same run; an epoch check discards late model responses. Approval requires a matching pending action and sufficient final speech confidence, or a click. Audio and the stream of partial transcripts are never persisted; recovered commands enter history only when submitted.

The native process owns an emergency-stop/manual-input event tap and checks its own stop latch during input. Its event loop remains independent of provider requests and the renderer. All generated events carry a marker; unmarked mouse/keyboard input pauses the run, and Escape cancels. Manual input content is not recorded. Capture and input remain disabled until OS permission is granted. Unsupported operating systems fail explicitly; the tutorial remains usable.

Private-local mode permits only literal loopback inference endpoints, rejects redirects and disallows cloud model identifiers. Private BYOM routes content directly to a user-configured provider. Telemetry is disabled; an allow-listed schema is available for a future opt-in sender. Sponsored routing is not enabled without a separately reviewed service.

Local AX hit-testing identifies editable fields, selection/navigation roles and an allow-list of benign activatable labels. Labelled buttons, menu items, checkboxes and radio buttons outside that list (in any language) and consequential words require approval; unlabelled or unidentified targets return `RETRY` without input. Protected applications, detected secure inputs and sensitive domains require takeover before capture. Safety metadata remains local. Separately, observations include bounded window titles, static accessibility text and selected text, plus recent window/document/task references as requested by the updated MVP specification. Credentials detected in this context are omitted before provider requests. User approval is tied to a frame; changed geometry, application or screenshot forces replanning. This classifier is intentionally limited and is not a general guarantee of semantic safety.

The native helpers are restarted in place by the main process after an exit or hang (500 ms–2 s backoff, at most five restarts per minute); pending requests fail with a recoverable unavailable error and an active run pauses with “Desktop control restarted.” Both helpers exit when their parent process dies.

`menu_item` and `click_control` act on what the model can name rather than where it points. `menu_item(path)` takes two or three menu titles; the helper resolves them against the live menu bar (a full title or a prefix ending at a word boundary, case-insensitively, ignoring a trailing ellipsis), opens the parent menu once when the item reports itself disabled or was not built yet, then presses it with `AXPress`. The Apple menu and any item that quits an application, logs out, restarts, sleeps, locks or shuts down are refused natively whatever policy decided; a resolved item's own title still goes through the consequential check, so a menu "Send" asks exactly as a button "Send" does. `click_control(label, role?, x?, y?)` resolves a name against the same control walk capture uses: exact names beat prefixes, a role narrows the set, and identical names are told apart only by the position the model read from `context.controls` — several equal candidates and no position is ambiguous, and nothing is clicked. Both are resolved again immediately before input and therefore skip the pixel revalidation a moving page would fail, keeping the same-application, same-window, display-geometry and stop-latch checks. `surface(action)` reports `menuStatus`/`menuLabel` and `controlStatus`/`controlLabel`, and for a chord it reports `shortcutLabel`, the menu item that chord invokes in this application, which lets an unknown chord be allowed as that application's own published command instead of a guess. Such a chord is then executed as that menu item (`hotkeyRoute` in `native/macos/NamedTargets.swift`): the helper resolves the path again immediately before input, requires the item to still carry the chord, reports a greyed-out or vanished one (`TARGET_DISABLED`/`TARGET_MISSING`, a rejected step whose error names only the chord, never the item's title), and never posts the keys in its place. A chord published for an item `menuPathRefused` rejects (CMD+Q, Finder's Empty Trash) is refused (`TARGET_REFUSED`) whichever way it would go, text chords included, and `surface` reports `shortcutStatus: "refused"` for it so policy refuses it instead of asking. Before an approval the focused-field revalidation does not apply because the item is the target. Every hotkey reaches native with the `shortcutLabel` policy judged it by (when `surface` reported one), and a chord that no longer names that item when it is about to be pressed is refused as `STATE_CHANGED` (`MENU_CHANGED`) instead of pressing an item policy never saw. An approved step is also marked `approved`: the runner's `revalidate` and the check inside `execute` then give it the full keyboard check (fresh capture, focused element, controls), because a menu command acts on whatever holds focus or selection, and the approval is spent if anything there changed. Text and clipboard chords (select all, bold/italic/underline, undo, redo, copy, cut, paste), modifier chords on arrows, Home/End, Page Up/Down and the delete keys, and chords no menu publishes are still posted as keys to the verified focused element. `execute` returns `via: "menu" | "keys"` for a hotkey, journaled on `ActionExecuted`. Edit-menu Copy, Cut and Paste items follow the hotkey clipboard rules: copy and cut are refused, and a paste the user asked for is sent back to CMD+V. `context.menus` carries the same menu map to the model every step, cached natively for four seconds per process.

The run loop recovers instead of failing where it can. Malformed model output (including text around exactly one embedded JSON object, which is extracted) and invalid actions are returned to the model as rejections; four in a row pause the run. A provider refusal pauses immediately. Transport retries stay inside the provider's 60-second deadline; two consecutive transient provider outages pause the run. Native stop latches, surface blocks (`SURFACE_BLOCKED` → takeover), changed screens, launch errors and helper loss each become a pause, takeover or rejection rather than a failed run. Executed-step history names the verified target (“Executed click on button “1”.”). Loop detection warns when the last four executed actions form a period-1 or period-2 cycle and pauses if it continues four more steps; switching apps with `open_app` in at least four of the last eight steps across two or more apps adds a one-time warning. The runtime budget counts only active time (paused, takeover and approval waits excluded). Saved settings apply to an active run: budgets immediately, protection lists at the next evaluation.

Local memory ([MEMORY.md](MEMORY.md)) makes repeated work faster. At run start the runner recalls, within a bounded budget, a small `MemoryContext`: relevant past episodes and corrections, frequently used apps, folders, recent and matching files from Spotlight metadata (never contents), and possibly a plan. Plans come from built-in intents (open an app, go to a site, search Google or YouTube, open a named file) or from skills learned from the user's own completed runs. A replay plan runs its steps without model calls, but each step still passes schema validation, policy, approval and native revalidation, and any mismatch hands the rest of the task back to the model. Pointer steps are stored by control role and label, never coordinates, and are resolved against the current frame's grounded controls. The store is one AES-256-GCM file sealed with the vault key; the Learning section in Settings shows counts and can forget everything.

The tutorial is a deterministic in-app simulation, clearly labeled. It exercises the same action schema, run loop, journal and contribution flow, but is not evidence that a model can operate the host desktop.

Contributions have a separate endpoint and explicit per-run review. Raw native screenshots are excluded from contribution in this alpha: OCR alone is not a sufficient privacy guarantee. Statistics and sanitized text/action metadata are supported. Synthetic tutorial frames can be included. A reference encrypted ingest service implements consent, checksums, resume, commit and deletion. It is for local development; production requires authenticated deployment, storage/KMS, retention operations and privacy review.
