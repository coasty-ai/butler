# The voice loop

The voice loop measures the distance to "I never have to type or use the mouse" the only way that counts: it **speaks** the suite's prompts through the speakers into the running, packaged Butler.app, watches what the app did from its own diagnostics and from the Mac's state (osascript), names each failure, and writes a content-free `results.json` and `report.md` that the fix loop (`docs/HARNESS_LOOP.md` §11) turns into fix lanes. Nothing is injected: the wake word, the recognizer, the routing, the run and the spoken reply are the real ones. It is the voice-level sibling of the bench harness cycle, whose §13 says "Voice is not measured"; this closes that gap.

```
npm run voice:loop -- --i-know-this-speaks-to-my-mac
  -> output/voice/<cycle>/{results.json, report.md, lanes/<CLASS>.voice.md, turns.jsonl, diagnostics/current.jsonl}
  -> npm run loop -- --output output/voice          (selectLanes / laneBrief, unchanged; writes lanes/<class>.md beside)
  -> you fix, rebuild and relaunch Butler.app (the loop never does)
  -> next cycle at the same suite hash compares class rates
```

## 1. What it never does

- **Never approves.** No turn says yes, sure, go ahead or any approval phrase (a suite invariant rejects them; `ask-deictic`'s "sure go for it" is allowed only because the task pins it to a question). A confirmation or a click asked for is **declined** with "`Hey Butler`, stop", and the loop verifies the run ended within 5 s.
- **Never speaks after an unheard prompt or a takeover.** "Stop" is spoken only for a run still going, a pending confirmation, a `needClick` plan or a hand-off (`request_user`), so a run waiting for a hand ends at once and not at the timeout; a late stop after an unheard prompt used to collide with the next one. A person at the Mac ends the cycle silently with exit 3; a run the takeover paused is yours to resume or stop. A takeover is `UserTakeoverStarted{manual_input}` or `NativeUserTakeover` **stamped since the current prompt** (the log tail fed at startup holds the session's earlier ones, and those are not this turn's), or an `HIDIdleTime` reset later than both the prompt and the app's own last `ActionExecuted` plus 3 s that is still unexplained 3 s later (10 s while a run is open: the helper posts its keystrokes first and the runner logs the step only when it returns, so the app's own typing must be given time to explain itself).
- **Never launches, relaunches, quits or packages the app.** Preflight refuses unless exactly one `release/mac-arm64/Butler.app` process is running (`NOT_PACKAGED_APP`). Rebuilding and relaunching are your steps between cycles.
- **Never the owner's data.** Suite invariants (`src/gym/voice/suite.ts validateSuite`, tested on the fixture) forbid Messages, Mail, FaceTime and the words send, pay, purchase, publish, install, delete my, empty trash, password; every `delete`/`rm` in a cleanup must be scoped on its line to the attempt's `{token}`, its `{benchDir}`, files `-newer {marker}`, or a Notes creation-time window with content words. Browsing uses example.com and en.wikipedia.org only; screenshots are deleted unopened; apps are quit only if the loop opened them; the output volume is restored after every task.
- **One agent on the desktop.** The same desktop lock as the cycle and the bench (`~/Library/Caches/open-assist/desktop.lock`, `script: "voice-loop"`), and `ps` is checked for another cycle or bench.
- **Content-free artifacts.** `results.json`, `report.md` and the briefs carry codes, ids, booleans, numbers and the fixture's own catalogue text; never a transcript, a reply, a URL, a path or a note body. Those go to the local `turns.jsonl` only, and a test feeds marked text through the report to prove it.

## 2. Requirements and preflight

The app must run **with verbose diagnostics** (`COARENA_DIAGNOSTICS_VERBOSE=1`): `Command.text`, `RunState.task` and `RunState.message` are verbose-only fields, and heard/misheard and the task-word checks depend on them. Preflight is read-only (`ps`, `ioreg`, `plutil`, `osascript -e 'get volume settings'`, `shortcuts list`, the diagnostics tail) and refuses with exit 2 on:

| Code                      | Meaning and remedy                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NOT_PACKAGED_APP`        | Not exactly one `release/mac-arm64/Butler.app` process with bundle id `ai.coarena.openassist`. Launch it yourself; a dev Electron is refused.                 |
| `HARNESS_RUNNING`         | A cycle, bench or another voice loop is running, or holds the desktop lock. Wait or stop it.                                                                  |
| `DIAGNOSTICS_NOT_VERBOSE` | The app's environment lacks `COARENA_DIAGNOSTICS_VERBOSE=1` and its newest `Command`/`RunState` carries no text. Relaunch with the variable set.              |
| `NOT_LISTENING`           | The latest `wake_status` says `listening: false`, or none was seen since the app started. Turn on "Hey Butler" in the tray; check the microphone.             |
| `PERMISSIONS`             | No `Permissions` event since app start, or one with screen, accessibility, microphone or speech false. Open Butler's Settings once; grant them.               |
| `VOLUME`                  | Output muted or below 35. The loop speaks at the volume it finds (`V`) and enforces it before every turn.                                                     |
| `RUN_LEFT_OPEN`           | A run started since the app's own launch is not terminal. Say stop to the app yourself or wait. (A run a crash cut off in an earlier session is not counted.) |
| `QUIET`                   | Only with `--require-quiet`: no standby trace (`BUTLER_TRACE_STANDBY=1`) to judge the room by. Without the flag this is a warning (`QUIET_UNKNOWN`).          |
| `TERMINAL_ACCESSIBILITY`  | The terminal itself lacks Accessibility, so System Events cannot see app windows and no setup could wait for one. Grant it in Privacy & Security.             |

Per-task **skips** (not refusals): the **Automation consent** probes, one per app the runnable tasks' setups or state checks send Apple Events to (`taskProbes`: Notes, TextEdit, Safari; a cleanup that only quits an app is not counted, its failure is logged). The first Apple Event from this terminal to an app raises macOS's consent prompt, and cycle 1 (2026-09-19 00:55) hung four setups for their 10-15 s on it with nobody at the Mac; tccd wrote the consent only at 00:59:15, when the owner came back and clicked (the `TAKEOVER` that ended the cycle). Probed at preflight, while the owner is still at the keyboard, a denial skips the app's tasks with `NOTES_AUTOMATION`, `TEXTEDIT_AUTOMATION` or `SAFARI_AUTOMATION`, and a probe that timed out or failed otherwise (a prompt still on screen) with the `_UNKNOWN` form. The probe obeys the setup rule itself (§4): an app that is not running is launched through LaunchServices (TextEdit with a probe document, so no open panel), its window awaited through System Events for up to 20 s, and only then sent the event; it is quit again only if it was not running (through Apple Events once the consent came; TextEdit, holding only the probe document, with `pkill` when it did not; Notes and Safari are then left as the prompt left them). `SHORTCUT_MISSING` (no Shortcuts shortcut named `Butler Voice Loop: Focus Off`) skips `sys-do-not-disturb`, and so does `SHORTCUT_UNKNOWN` when `shortcuts list` itself failed or timed out: a probe that could not be read is a failed probe, never a pass, because the task's cleanup needs the shortcut to turn Focus off again. Safari's "Allow JavaScript from Apple Events" is not required: the checks that need it are `optional` and read as unknown.

Numeric flags (`--idle-seconds`, `--rate`, `--repeat`) are validated like `--time-box`: a value that is not a number exits 2 rather than becoming a `NaN` every gate comparison would pass.

## 3. Running a cycle

`npm run voice:loop` is `node scripts/voice-loop.mjs`; the script is the I/O shell only (it speaks, polls the diagnostics log, runs osascript and writes files), and every rule lives in the pure modules `src/gym/voice/{suite,grade,classify,report}.ts`, tested in `tests/voice-loop.test.ts`.

```sh
npm run voice:loop -- --dry-run                         # validate the suite, print preflight facts and the plan; speaks nothing
npm run voice:loop -- --dry-run --only fast-start       # ids, tags or categories, comma-separated
npm run voice:loop -- --repeat 3 --i-know-this-speaks-to-my-mac        # the recommended real cycle (~2 h)
npm run voice:loop -- --noisy --i-know-this-speaks-to-my-mac           # include the three noisy-room tasks
npm run voice:loop -- --idle-seconds 45 --voice Samantha --rate 175 --wake "Hey Butler" --i-know-this-speaks-to-my-mac
npm run voice:loop -- --report-only 20260919-2200-75ed88e              # re-render from the ledger
npm run voice:loop -- --rehearse --only app,dictation --i-know-this-speaks-to-my-mac   # setup + cleanup of each task once, nothing spoken
```

`--rehearse` runs every selected task's setup and then its cleanup, once, and prints each step's exit code and time (and a failed step's detail): the way to prove a setup cannot hang before a cycle spends an evening on it. It needs no Butler.app and speaks nothing, but it opens and closes windows on this Mac, so it takes the desktop lock, runs the consent probes and requires the consent flag; only `HARNESS_RUNNING`, `PRESENCE_UNKNOWN` and `TERMINAL_ACCESSIBILITY` refuse it.

Leave the Mac after starting it: no prompt is spoken until `HIDIdleTime` is at least `--idle-seconds` (45), and after any human input the full idle is required again. Between tasks only "no input since the app's own last `ActionExecuted` plus 3 s" is needed, because the app's synthetic clicks move `HIDIdleTime` like a hand would (`presence.ts idleRequired`). Ctrl-C once stops after the current turn (a running run is stopped, cleanup runs, reports are written); twice exits at once.

**The per-task gate** (`src/gym/voice/grade.ts voiceGate`, polled every second, cap 10 min, in this order): no open run (`RUN_OPEN`; trial 05:43 showed a run left paused turns the next prompt into `resume_refused`), no open follow-up window (`FOLLOWUP_OPEN`), 800 ms since the app last spoke (`SPEAKING`, the echo guard), 5 s with no non-chatter event (`BUSY`), `wake_status listening: true` (`NOT_LISTENING`), a quiet room when the standby trace is on (`NOISE`: the two newest `standby_trace level` rms under the threshold, and no `textLength > 0` trace in 10 s), the volume at `V` (`VOLUME`), and idle (`HID_ACTIVE`). The quiet threshold starts at `max(3 × floor, floor + 4)` from the preflight's median level and tightens to `floor + 0.35 × (speech − floor)` only once a level inside one of the loop's own `say` windows is clearly speech (`isSpeechSample`: at least twice the floor and 5 above it); the standby engine stops emitting levels at `wake_detected`, so most say windows hold only a pre-speech room sample, and a threshold calibrated from one would collapse to the floor and block on ordinary room noise. Setup runs after the gate, and the gate is checked once more before speaking. Every wait is logged with its account (`grade.ts GateWait`): the refused polls and the time they cost by reason, whether the gate opened or gave up. Cycle 3 (2026-09-19 09:07) waited ten minutes after its first turn, `FOLLOWUP_OPEN` for the window's 45 s and then `HID_ACTIVE` (a person using the Mac, the helper's `NativeInputIdle` reports every few seconds, an emergency stop at 09:16), and stopped on the cap; the wait was logged only when the gate opened, so the report said "gate waited 1 time(s), 0 s in all. Stopped early: GATE_CAP". Now the **cap** (`GATE_CAP`, 10 min) counts refused time only, and the report says which turn gave up, how long on what, and what the dominant reason means ("Stopped early: GATE_CAP (app-switch-safari#1 waited 600 s: HID_ACTIVE 555 s, FOLLOWUP_OPEN 45 s)"; the Gate section repeats it in words). One reason held **two minutes without a break** is the app's own fault and is named as such, with evidence, instead of the cap: `RUN_OPEN` → `RUN_LEFT_OPEN` (the open runs' statuses and how long since they last changed), `FOLLOWUP_OPEN` → `WINDOW_STUCK` (the window's kind, how long open, how often it reopened: a conversation window renewed by every exchange is someone talking to the app, not a hang), `NOT_LISTENING` → `NOT_LISTENING` (how long since the last `wake_status`); these abort the cycle with exit 3 like a run left open after a turn, and nothing more is said. The room's reasons (`HID_ACTIVE`, `NOISE`, `BUSY`, `SPEAKING`, `VOLUME`) run to the cap, since a person at the Mac or a loud room is not the app's fault.

**The turn.** A marker file is touched, the diagnostics offset noted, the prompt spoken as `"<wake>, <say>"` (one `say` call; the comma is the pause the wake rule needs), then events are polled every 250 ms until (`grade.ts lastTurnDone`): a terminal `RunState`; for a `stopRunAfter` task the expected steering outcome (`pause`, `resume`, `stop`) observed and 2 s settled, so a run meant to keep going does not run out the timeout as `RUN_INCOMPLETE`; an answer or question with 6 s of quiet; no wake within `unheardMs` (20 s; nothing more is said); a confirmation, `needClick` or hand-off (declined with stop); a takeover (cycle aborts); or the task's timeout (a run still going is stopped and graded `RUN_INCOMPLETE`). Later utterances of a multi-turn task fire on their trigger (`ActionExecuted`, `RunState paused`, `SpeechOut requested` for barge-in, `followup_open` for the continuation window) and wait out the app's speech unless barging in, on freshly read events. A `followup_open` trigger does not fire on the first window: the app opens one right after the transcript and closes it ~300 ms later (`endReason: "speaking"`) to say its ack, then opens another after `speech_finished`, and a line spoken into the first lands on a closed microphone (trial 05:43 #2, both follow-up tasks `UNHEARD`); the line goes into a window that is open, of the trigger's kind, with the app not speaking and no `SpeechOut requested` pending, checked before and after the `plus` delay (`grade.ts followupReady`, `watch.ts AppWatch`). The run status is carried from one utterance to the next (`summarizeUtterances`): the app writes `RunState` only on a change, so the `continue` turn sees the pause the `wait` turn left and its resume counts. Then state checks run (osascript), cleanup runs (always, in a `finally`, a crash included), the volume is restored, and `results.json`/`report.md`/`lanes/` are rewritten. If the run is still open after a stop the cycle aborts (`RUN_LEFT_OPEN`). A `say` that fails (a missing voice, a lost output device) grades the turn `ENV_NOT_READY/SAY_FAILED`, cleans up and stops the cycle (`stoppedBecause: SAY_FAILED`); any other crash still writes `results.json` with `stoppedBecause: CRASHED` and releases the lock.

## 4. The suite

`tests/fixtures/voice-suite.json`: 39 tasks in nine categories (app, dictation, browsing, question, correction, multi-step, system, wake, noisy); 36 without `--noisy`, minus the probe skips. Each task has `say` (what follows the wake phrase), `heard` (a regex over a transcript that carries no punctuation, so `\bnotes?\b`, never `Notes,`), an `expect` (outcome `answer | run | question | stop | pause | resume | revise | confirmation | silence | interrupt`, with `runCompleted`, `noConfirmation`, `taskWords`, `frontmost`, `state` checks, `replyHas`, `noMutation`, `maxActions`, `actionTypes`), `setup`/`cleanup` scripts with `record` for values later steps read as `{state.<name>}`, `tags`, `notes`, and optional `turns[]` for multi-utterance tasks. Placeholders: `{token}` (`voiceloop` + 4 base-36 chars), `{benchDir}` (`~/OpenAssistBench/voice-{token}`), `{wake}`, `{marker}`. The default selection's estimate (Σ timeouts + 12 s a task) must stay under an hour; the test checks it.

**The setup rule: setup talks to apps only after a window exists.** An Apple Event to an app that is still launching, or that sits behind the terminal's consent prompt or a panel, waits for it, and in cycle 1 the wait ran out four setups' 10-15 s timeouts (`count windows` after `open -a TextEdit`, Safari's `make new document` at cold launch). So a setup never sends an Apple Event to TextEdit or Safari before a `poll` step has seen a window of theirs through System Events (`validateSuite` refuses it unless the script is guarded by `application "X" is running`), and it never sleeps a guessed second: a step with `"poll": true` is re-run every `intervalMs` (250) until its stdout is exactly `true`, bounded by its `timeoutMs` (60 s at most for any step), with every try bounded at 2 s, so a stuck osascript is killed and asked again and can never eat the whole budget, no try started with under 0.5 s left (the first rehearsal gave its last try the 4 ms that remained and the kill read as a hang), the poll ending when it said it would, and its detail naming what the last try that answered said plus how many tries hung (`suite.ts pollUntilTrue`). The loop's own documents are opened through LaunchServices, never by scripting a fresh app: a temp file named with the attempt's token (`/tmp/butler-voice-loop-{token}.txt`, or `.rtf` where bold must be possible, or a file in `{benchDir}`), `open -a TextEdit <file>`, then a poll for a TextEdit window whose name contains the token; only then is TextEdit counted or read. Safari is given a window when it has none: the first rehearsal (2026-09-19) found it running with zero windows, so `open -a Safari` did nothing and every Safari task waited its 20 s for a window that never came; now a step counts its windows through System Events (zero when not running) and runs `open -a Safari about:blank` only then (recorded as `safariLaunchWindow`), the window is awaited, and the task's script sets its URL on that window rather than making a new document, so the cleanup that closes the task's window by id leaves Safari as it was found; a Safari that already had windows gets a `make new document` as before. Calculator has no scripting terminology (a probe hung more than 12 s), so it takes no Apple Event at all: `open -a Calculator`, a System Events poll for its window, and `pkill -x Calculator` at cleanup, only when the loop launched it (the one kill a script may carry, and only on a line guarded by a recorded was-running value). Cleanups close the loop's documents by token (`saving no`), delete only the temp files it made, and quit only the apps it launched (`quit saving no` for TextEdit, since everything in it is then the loop's); Notes keeps its preflight probe (§2) since a note can only be made by scripting it.

The suite hash (`sha256` of the fixture plus `grade.ts` and `classify.ts`) is stored in every `results.json`; cycles at different hashes are never compared.

## 5. Grading and failure classes

`summarizeTurn` (the trial prototype's summary, typed) reads one utterance's events from the moment `say` started: `wakeMs`, `transcriptMs`, `endpointMs` (transcript − say end), plan, decided act and code, early start, run, actions and mutations, confirmations, takeover sources, status timeline, spoken reply and its latency, follow-up window, speech, standby levels, capture timings. **Heard** means the wake phrase within 15 s and the task's key words in the transcript (lowercased, punctuation stripped); **misheard** means a transcript without them; **unheard** means neither. `gradeTurn` applies the expectation and the osascript evidence to a heard or a misheard turn (never an unheard one, whose state could only mask the miss); `classify` names the turn, first match wins, and a misheard turn whose outcome and checks passed is a pass with the soft `MISHEARD_DONE` (row 13) rather than the failure `MISHEARD` (row 5), since the owner felt nothing:

| #   | Class               | When                                                                                                                                                                                                                                                                                      | Fine owner      | Cost |
| --- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | ---- |
| 1   | `ENV_NOT_READY`     | A preflight or gate refusal for the turn (`subcode`: `NOT_LISTENING`, `SETUP_FAILED`, `RUN_LEFT_OPEN`, …)                                                                                                                                                                                 | harness         | 0    |
| 2   | `TAKEOVER`          | A person touched the Mac; the cycle aborts and says nothing                                                                                                                                                                                                                               | user            | 0    |
| 3   | `UNHEARD_NOISY`     | Unheard, task tagged `noisy`                                                                                                                                                                                                                                                              | recognizer/gate | 2    |
| 4   | `UNHEARD`           | Unheard                                                                                                                                                                                                                                                                                   | recognizer/gate | 3    |
| 5   | `MISHEARD`          | Heard something else, and the outcome failed too (a transcript without the key words whose run still did the right thing is the soft row 13: cycle 2, 2026-09-19 01:11, "open a new text window" and "quick calculator" each completed in one action with every check true)               | recognizer/gate | 4    |
| 6   | `WRONG_PLAN`        | Heard, but the wrong kind of thing happened: a run for a question, an answer for a command, `resume_refused`, `FALSE_WAKE`, wrong task words, a late stop                                                                                                                                 | dialog core     | 5    |
| 7   | `NEEDS_CLICK`       | `noConfirmation` and a `PolicyConfirmationRequested`, a `needClick` plan, or a hand-off takeover (`request_user`, `handoff`, `policy`, `surface`)                                                                                                                                         | runner/policy   | 10   |
| 8   | `RUN_FAILED`        | Terminal `failed`, or cancelled by the app itself                                                                                                                                                                                                                                         | runner/policy   | 6    |
| 9   | `RUN_INCOMPLETE`    | Still going at the timeout (the loop stopped it), or not completed where completion was required                                                                                                                                                                                          | runner/policy   | 6    |
| 10  | `WRONG_STATE`       | Completed, but a state, frontmost, reply or mutation check is false (`FALSE_DONE` when the check is `primary`). A non-optional check that could not be read is `ENV_NOT_READY/STATE_UNREADABLE` (grader debt), judged just before this row so it never masks an unheard or misrouted turn | runner/policy   | 8    |
| 11  | `SLOW_FIRST_ACTION` | _Soft_: passed, but the first action came more than 4 s after the transcript                                                                                                                                                                                                              | runner/policy   | 2    |
| 12  | `SLOW_REPLY`        | _Soft_: passed, but the reply came more than 3 s (answers) or 2 s (acks) after the transcript                                                                                                                                                                                             | dialog core     | 1    |
| 13  | `MISHEARD_DONE`     | _Soft_: heard as other words (row 5's transcript), yet the outcome and every state check passed; the turn passes and counts as hands-free                                                                                                                                                 | recognizer/gate | 1    |

A turn has at most one hard class and may add one soft class; soft classes never fail it. `TAKEOVER` and `ENV_NOT_READY` are reported apart under Environment and excluded from the ran-turn denominator (`ENV_NOT_READY` subcodes include `SETUP_FAILED`, `RUN_LEFT_OPEN`, `STATE_UNREADABLE`, `SAY_FAILED` and `SPEECH_ENDED_BEFORE_WAKE`, a barge-in the loop started after the reply had already ended). A `SETUP_FAILED` turn's record carries `setup`: the failed step's index and kind, its exit code, its time and the first 80 characters of what it said (the home folder as `~`; a poll's stderr says `poll <tries>x/<ms> ms: <the last try's words>`), and the Environment section prints it per turn, so the next report says why and not just that. The whole stderr goes to the local `turns.jsonl` only. Classes are ranked by count × cost; a soft class counts the passed turns over its budget (the report says "passed turn(s) over budget") so it can earn a lane and a brief like any other, while the pass rate never moves for it; rates carry Wilson 95% intervals, so at n ≈ 33 a class needs three hits to earn a lane, which is why `--repeat 3` is the real cycle. `NEEDS_CLICK` and `WRONG_STATE` are the trust breaches: fixed only at 5% with the interval under it (10% for the rest).

Latency budgets (`grade.ts LATENCY`): wake ≤ 3 s after `say` starts, endpoint ≤ 3.8 s after it ends, first action ≤ 2.5 s after the transcript (class at 4 s), reply ≤ 1.5 s (class at 3 s / 2 s), capture total ≤ 900 ms. The report prints p50/p95 of each.

## 6. Output and the fix loop

`output/voice/<cycle>/` holds `plan.json`, `ledger.jsonl` (append-only; `--report-only` re-renders from it), `results.json` (schema 2 superset: `kind: "voice"`, `failureClasses` in the bench's exact `FailureClass` shape), `report.md`, `turns.jsonl` (local: transcripts, task text and messages), `diagnostics/current.jsonl` (the collected event slices, each with `voiceTurn: "<taskId>#<attempt>[/t<n>]"` so a brief's example run ids resolve by grep), and `lanes/<CLASS>.voice.md` (the voice fix brief per class: the mechanism note prefixed with the fine owner and the files it names, the evidence to open, the example turns, the floors, the voice probe). The `.voice.md` suffix keeps it apart from the `lanes/<class>.md` the fix loop writes into the same folder: on the default case-insensitive APFS `UNHEARD.md` and `unheard.md` are one file, and the loop's brief carries the bench probe.

Because `results.json` is schema 2 and `failureClasses` map fine owners to the loop's (recognizer/gate, dialog core, runner/policy, native → `agent`; harness → `harness`; `STATE_UNREADABLE` → `grader`; `TAKEOVER` → `user`, never a lane), the fix loop reads it unchanged:

```sh
npm run loop -- --output output/voice                 # lanes and briefs from the newest voice cycle
npm run loop -- --output output/voice --create-lanes  # + a worktree and branch per lane
```

`laneBrief` prints the class note verbatim, so the brief carries the owner and the evidence pointer. Every brief repeats the two rules: **a safety floor is never relaxed** (`src/core/policy.ts`, `src/voice/turns.ts`, `native/macos/WakePolicy.swift`, `native/macos/TurnPolicy.swift` and the other `FLOOR_PATHS` may gain a rule, never lose one; a refusal that costs a `NEEDS_CLICK` stays, the route must avoid the control or you accept it), and **the loop never merges**. The probe for a lane is your command: rebuild and relaunch the app, then `npm run voice:loop -- --only <the class's task ids> --repeat 3 --cycle-id probe-<class>-<id> --i-know-this-speaks-to-my-mac`, and compare against the cycle at the same suite hash (the report's "Against the previous cycle" table: `improved / regressed / inconclusive / new / gone`, one-sided p < 0.05; at n ≈ 33 most verdicts are inconclusive and the report says how many attempts a 10-point change would need).

## 7. Reading the report

1. Header: cycle, git rev, app version/build/executable mtime, voice/rate/wake, idle, noisy, quiet calibration (floor/speech/threshold or "no trace"), suite hash, time used, gate waits, why it stopped early.
2. **North star**: hands-free success (passed with zero confirmations and zero clicks asked for, over ran turns, with its interval) and p50/p95 of first action, reply, wake, endpoint and capture.
3. Pass rate by category and tag (italic under n = 12).
4. Failure classes by count × cost: owner, count, rate [interval], seconds lost, categories, example turn ids, the mechanism note, the evidence line.
5. Environment: takeovers and not-ready turns, and the abort if any.
6. Against the previous cycle.
7. Per-turn table, gate log, preflight facts and skipped tasks with remedies.

## 8. Limits and open points

- Quiet thresholds (the `max(3 × floor, floor + 4)` fallback, `floor + 0.35 × (speech − floor)` once calibrated, the `isSpeechSample` bar) and the `[[volm]]`/`[[slnc]]` speech markup are unconfirmed constants; the report prints the calibration (or `speech null` when no sample was ever captured) so they can be tuned.
- The HID takeover rule waits 10 s for the app to explain a reset while a run is open; a `type_text` longer than about 200 characters (50 ms a character) can outlive that and read as a person. The app's own `NativeUserTakeover` covers runs in any case.
- `Permissions` is logged only on the Settings IPC and the verbose flag is inferred from the app's environment or its newest events; logging both at app start would let preflight tell without a prior command.
- The DND assertion file's shape on this macOS is unconfirmed, so `sys-do-not-disturb` grades on run completion with an optional check.
- A person reading without touching is invisible to the gate, as in the bench.

## 9. Acting as you speak: the streaming report

While a person speaks, the app commits each clause of the growing partial and acts on the navigational ones before the sentence ends (`docs/VOICE_PRODUCT.md` "Acting as you speak"; design `.data/design/streaming-execution.md`). `scripts/streaming-report.mjs` reads what that left in the diagnostics stream, the app's own log or the copy a voice cycle keeps, and says per turn what committed, what acted, how fast, whether the final kept it and whether the run then repeated it; `tests/streaming-report.test.ts` runs it on a synthetic stream.

```sh
node scripts/streaming-report.mjs                                        # the last 20 turns of .data/diagnostics/current.jsonl
node scripts/streaming-report.mjs --turns 200 .data/diagnostics/current.jsonl.1 .data/diagnostics/current.jsonl
node scripts/streaming-report.mjs --json output/voice/<cycle>/diagnostics/current.jsonl
```

**What it reads.** Content-free, like the endpoint report: of a `VoiceEvent` row the phase and the timestamp; of the four streaming events their allow-listed codes and measurements alone; around them only `NativeRequest.method`, `RunStarted`, `ActionExecuted.actionType` with its `early` flag, `ModelRequestStarted` and `SpeculationStarted`. It never reads `text`, a URL, a label or an app's name, so it cannot print them; the test feeds a sentinel through every text field of every row (the streaming rows included, which the app never writes such fields on) and asserts it is absent from both outputs. The events:

| Event                   | Fields                                                                                                                                                                                                                                                                                                                                                                                                                                        | Written when                                                                                               |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `StreamClauseCommitted` | `index` (0-based order in the utterance), `by` (`boundary`: the next clause's first content word arrived; `stable`: 350 ms unchanged as verb + object), `words`, `leadMs`, `superseded` (true on a re-commit of an index: the clause grew or was rewritten and committed again)                                                                                                                                                               | a clause of the partial commits, while the person is still speaking                                        |
| `StreamedAction`        | `kind` (`open_app`, `open_url`, `scroll`), `siteKey` (the recipe table's key, `open_url` only), `nav` (`home`: a site's front page; `query`: an address with an object in it), `clauseIndex`, `decideMs` (the rules, and Jev when they were unsure), `issueMs` (from the commit; a query's includes the 350 ms hold for the words to stop growing), `reissue` (true when it replaced an earlier issue of the index, the earlier step dropped) | a fast action is issued for a committed clause, after the policy allowed it with `speaking` set            |
| `StreamedActionDropped` | `kind`, `clauseIndex`                                                                                                                                                                                                                                                                                                                                                                                                                         | the final no longer contains a clause that acted (the recognizer rewrote it, or the person changed course) |
| `StreamedRunStarted`    | `streamedSteps`, `dropped`                                                                                                                                                                                                                                                                                                                                                                                                                    | the run starts with the prelude that names the streamed steps and the dropped ones                         |

A turn is the rows from an activation to its outcome, plus the rows that follow before the next activation (the final's drops, the prelude, the run's own steps). Each fast action is paired with the last commit of its `clauseIndex` and with the fast-route `NativeRequest` (`execute`, `open_url`, `open_app`, `scrollContinuous`) nearest its row between the commit and the row plus 250 ms, each request claimed once; commit → issue is the commit's row to that request's, or to the action's own row when none is found (the line then says `commit -> issued` and the summary counts it under `from the event`). A `StreamedActionDropped` names the latest earlier action of its index (and kind) not yet dropped, so a reissue reads as one step dropped and one kept. The run's `TransitionSettled {kind: navigated}` after `RunStarted` is its first capture waiting for the prelude's last page; the settle wait is `RunStarted` to that row.

**Once per thing asked** (the line after the clause totals, and per turn `clauses N (M commits, K re-commits)`, `navigations N (K reissued)`, `(re-commit)` on a clause line, `home`/`query` and `reissued` on an action line, `first capture settled … in` on the run line): the live evening of 2026-09-19 had one growing clause committed seven times at one index and its query issued three times in 1.2 s, four navigations in one seven-second sentence, and the run's first click failing on a page still loading. The goal is commits per clause anything, issues per clause max 1, navigations per sentence equal to the sites and searches asked for, reissues only on a spoken correction, and every run with a prelude settled.

**Per turn** one head line (activation, outcome, clauses, fast actions, dropped, prelude size, repeats), one line per clause (`clause 1 by stable, 4 words, lead 1950 ms, -> final 1950 ms: open_url youtube decide 170 ms, issue 50 ms, commit -> request 200 ms; kept`, or `no fast action`, or `dropped by the final`), one line for the run (how long after the final it started, the prelude's counts, and `repeated open_url gmail 1700 ms in` or `no repeat`) and, when any, the model requests made before the final. A turn with no committed clause prints one line. `--json` gives the same as data (`summary`, `turns[]` with `clauses`, `actions`, `dropped`, `run`).

**Summary and targets.** The summary covers the turns with a committed clause among the last N:

| Measure                               | Target                                  | Where it is read                                                                                                                                                                                                                                                                                                        |
| ------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| clause committed → fast action issued | ≤ 250 ms p50, ≤ 600 ms p95 (site opens) | the `commit -> issue` line, which says `met` or `missed` over the site opens (and actions from logs before `nav`), with the queries' own numbers beside, since a query is held 350 ms after a stable commit for the words to stop growing; `decideMs` and `issueMs` split the budget between the decision and the route |
| issues per clause                     | max 1                                   | the `Once per thing asked` line: `issues per clause p50 … max …`; a max above 1 means an index navigated twice, which only a spoken correction (`reissued`) should produce                                                                                                                                              |
| navigations per sentence              | the sites and searches asked for        | the same line: `navigations per sentence p50 … max …` with site opens, queries and reissues; a sentence naming one site and one search is 2                                                                                                                                                                             |
| first capture settled                 | every run with a prelude                | the same line: `first capture settled in N of M runs (n= p50 … p95 …)`; a run not settled started its first look on a page it had not waited for                                                                                                                                                                        |
| model calls before the final          | 0                                       | `before the final`: `ModelRequestStarted` rows between the activation and the outcome, in turns with a clause; the speculative request of "Thinking ahead" is counted beside so it can be told apart (it is the one model request the design allows before the final, and it is not the stream's)                       |
| the run repeats a streamed step       | 0 % of runs with a prelude              | `repeats`: after `StreamedRunStarted`, a journaled `open_app`/`open_url` (never an `early` one) of a kind the turn streamed and, when both rows carry a `siteKey`, the same key; a repeat means the prelude was ignored, which is prompt work in `src/providers/http.ts`, not the stream's                              |
| wrong fast action                     | navigate again; nothing to undo         | `dropped`: the share of fast actions whose clause the final no longer said; each is a page or app opened for nothing, the cost of committing early, and a rising rate points at the stability window or the boundary rule (`by` says which committed the clause)                                                        |
| cost                                  | ≤ 1 Jev call per committed clause       | not in the stream yet: the clause question has no event of its own; a `decideMs` near Jev's ~160 ms warm answer says it was asked, one near zero that the rules decided                                                                                                                                                 |

**Reading a miss.** A high `decideMs` is the decider (Jev's 600 ms ceiling, or the rules waiting on it); a high `issueMs` is the route (the AppleScript to a browser window, or the `open -a` fallback when the safe window is missing); a commit → request far above `decideMs + issueMs` is queueing between them (the main process busy, or the helper slow: look for `NativeSlow` in the same window); `from the event` on many actions means the request rows were not matched, so check the route's method name against the script's list; a small `leadMs` with `by boundary` means the clause committed late, at the next clause's first word, when it should have committed by stability. Two limits: the controller sends an `open_app` as `execute`, so a request row alone never names the kind (repeats are read from the journal's `actionType`, and from requests only where the route's method is `open_app`/`open_url`), and a model `open_app` after a streamed `open_app` counts as a repeat whatever the app, since neither row names it.
